# 平台验证报告（Windows 单机）

| 项       | 内容                                                 |
| -------- | ---------------------------------------------------- |
| 对应任务 | T-M0-11（长路径与文件锁）、T-M0-10 / T-M0-12（待补） |
| 日期     | 2026-11-16                                           |
| 环境     | win32 / Node v24.16.0 x64                            |
| 复现方式 | `node scripts/spike/win-path-lock.mjs`               |
| 结论性质 | 本机实测（L3 的一次采样），不代表全部客户端环境      |

## 1. 长路径

| 检查                  | 结果                                   |
| --------------------- | -------------------------------------- |
| 构造路径长度          | 586 字符（14 级目录 + 180 字符文件名） |
| 是否超过传统 260 上限 | 是                                     |
| 写入 / 读取           | 成功，可 stat 到字节数                 |

结论：Node 在 Windows 上自动使用长路径前缀，内容寻址路径不含用户文件名，天然规避 260 字符问题。**但外部工具仍是风险点**：PowerShell 5.1、部分 CLI 与旧版安装器对长路径支持不一致，安装脚本与运维脚本必须使用短路径工作目录。

## 2. rename 与文件占用

| 场景                               | 结果                                       |
| ---------------------------------- | ------------------------------------------ |
| 本进程持有读句柄时 rename          | 成功，未被阻塞                             |
| 外部进程以不共享删除方式独占时删除 | 首次失败，错误码 `EBUSY`                   |
| 重试                               | 11 次（每次间隔 250 ms，约 2.75 秒）后成功 |

结论：

- Node 自身句柄不会阻塞 rename/delete，因此"合并过程中改名"不需要额外绕行。
- 真正的阻塞来自杀软扫描、编辑器或其他进程的独占打开，表现为 `EBUSY`。**必须保留重试**：退避重试上限 20 次，超限映射为统一存储错误码并记录审计，不得静默失败。
- 删除在句柄打开时也可能返回成功，但外部独占时不会。回收站物理清除任务需对 `EBUSY` 单独重试并记录。

## 3. NTFS 大小写

| 检查                       | 结果 |
| -------------------------- | ---- |
| 大写文件能否用小写路径访问 | 能   |

结论：文件系统大小写不敏感，**同名唯一性不能依赖文件系统**，必须由数据库 `lower()` 唯一索引保证（与 ADR-004 一致）。前端重名提示同理，需要服务端判定。

## 7. Nginx for Windows 接入层（T-M0-10）

| 项       | 内容                                                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------- |
| 版本     | Nginx 1.30.6 Stable（Windows 构建，单 worker）                                                        |
| 复现方式 | `node scripts/spike/nginx-throughput.mjs http://127.0.0.1:18080/files/test.bin <并发> 8388608 <轮次>` |
| 测试对象 | 1 GB 测试文件，Range 请求每次 8 MiB                                                                   |
| 场景限制 | 回环地址 + 文件缓存命中，**不代表磁盘或千兆网卡上限**，L3 单次采样                                    |

| 并发 | 请求数 | 状态分布  | 聚合吞吐    | 最大延迟 | P95 TTFB |
| ---- | ------ | --------- | ----------- | -------- | -------- |
| 20   | 100    | 206 × 100 | 2969.5 MB/s | 269.4 ms | 150.6 ms |
| 50   | 100    | 206 × 100 | 895.6 MB/s  | 893.2 ms | 693.6 ms |

结论：

1. **20 与 50 并发均无 5xx**，Range 响应全部为 206，静态下发链路可用。
2. **单 worker 的排队效应明显**：并发从 20 升到 50，聚合吞吐反而从 2969 降到 895 MB/s，最大延迟升至 893 ms。并发拉高不等于吞吐拉高，限流应按"在途请求数"而非"连接数"设计。
3. **文件正文不交给 Nginx 下发**的决策得到支持：单 worker 下大文件传输会挤占反代能力。
4. **HTTP/2**：二进制编译参数含 `--with-http_v2_module`，但本机 curl 不支持 h2c 探测，**未做端到端验证**；建议在 M0-14 配置 TLS 后，用 Node `http2` 客户端或浏览器补测，再决定是否启用。
5. 建议基线：`worker_connections` 1024、`keepalive_timeout` 65 s、限流按 10 并发上传 + 20 并发下载配置、分片 8 MiB 且超限在传输前拒绝。

对现有设计：无推翻；补充"并发升高吞吐反降"的观测，用于 M0-14 的限流参数。
