# ADR-006 备份工具与策略

| 项       | 内容                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状态     | Accepted（2026-11-16）                                                                                                                                                        |
| 决策者   | 开发方（单人开发）                                                                                                                                                            |
| 关联     | `docs/design/design.md` §2.9、§7.3、§8.6、§9.5、R2、R4；`ADR-004`、`ADR-005`                                                                                                  |
| 需求依据 | REQ-N-18（RPO ≤24 h；RTO 分级：单文件/单项目 ≤8 h、全库 ≤48 h；至少一份物理隔离离线备份）、OQ-12（现有介质、每日增量 + 每周全量、不异地）、REQ-N-04a（无 UPS 的缓解措施之一） |

## 背景

需备份两类数据：① 对象存储区（业务可用约 11.41 TiB，L2 理论值，内容不可变、增量天然友好）与预览缓存；② PostgreSQL（元数据、审计、任务、会话）。

约束：完全离线；无新增采购、使用现有可移除介质（OQ-12）；无 UPS，RAID5 重建窗口存在（R2）；单人运维，恢复流程必须可重复演练；备份介质可能被带离现场，需加密。

## 决策

采用 **restic（单二进制）+ `pg_dump -Fc`**，由 T-05 备份任务统一编排。

- 对象区：`restic backup` 到离线介质上的加密仓库；内容不可变 + 内容寻址，使增量与去重天然成立。
- 数据库：`pg_dump -Fc` 落临时目录后由 restic 一并入库，避免明文 dump 长期驻留。
- 策略：**每日增量快照 + 每周完整快照**；保留策略按"最近 30 天每日 + 最近 12 周每周 + 每季度 1 份"，最少保留 1 份物理隔离离线副本（REQ-N-18）。
- 完整性：每次备份后 `restic check --read-data-subset=x%` 抽样校验；每月一次全量 `check`（与 T-03 错峰）。
- 加密：仓库 AES-256，密钥由口令经 scrypt 派生；口令离线保管、不入仓库、不入应用配置，登记轮换步骤。
- 恢复：`restic restore` + `pg_restore`，分两级——**单项目/单文件级**（目标 ≤2 h）与**全库级**（L2 估算 7–22 h，取决于介质读速 500–150 MB/s）。
- 演练：M4 起每季度一次"从离线介质恢复到空环境"，记录实测 RTO 与失败点。

**平台说明（ADR-007）**：Windows 下脚本为 `backup.ps1` / `restore.ps1` 封装 `restic.exe` 与 `pg_dump.exe`；备份介质按卷标/GUID 解析，不写死盘符；不使用 VSS。**RTO 口径更新为 REQ-N-18 分级（单文件/单项目 ≤8 h、全库 ≤48 h，D3 已定）；脚本形态被 ADR-007 取代。**

## 备选方案与否决理由

| 方案                                    | 否决理由                                                                          |
| --------------------------------------- | --------------------------------------------------------------------------------- |
| borgbackup                              | 功能相当，但依赖 Python 与 C 扩展，离线部署面更大；单二进制交付更省事             |
| rsync + tar                             | 无加密、无内容级校验、增量靠 `--link-dest` 硬链接（介质文件系统受限），恢复粒度差 |
| PostgreSQL 物理备份 + WAL 归档（PITR）  | 可实现秒级 RPO，但对单人运维过重；本需求 RPO 24 h，逻辑备份足够                   |
| 数据库自带 `pg_dump` 全量每日（不增量） | 元数据量小可接受，但对象区 11.4 TiB 无法每日全量，必须增量                        |
| 商业备份软件 / 快照硬件方案             | 无采购；且与离线交付目标冲突                                                      |
| 云对象存储归档                          | 违反 REQ-C-03/REQ-N-33 与外流约束                                                 |

## 后果

**正面**：单二进制、无运行时依赖、离线可交付；加密满足介质带离现场；增量去重使每日备份窗口可控；`check` 提供可验证的完整性；恢复粒度可到单文件。

**负面**：① **RTO 与数据量强相关**：全库 11.4 TiB 在 150 MB/s 读速下约 22 h（L2）；REQ-N-18 已分级（单文件/单项目 ≤8 h，全库 ≤48 h，D3 已定），22 h 落在 48 h 内，但介质读速若低于上述假设则不达标。② 介质容量若小于"数据量 × 1.2"将无法保留多版本快照，需改为"永续增量 + 单一代"策略。③ 密钥遗失等于备份不可用，必须双份离线保管。④ RPO 24 h 意味着最多丢失一天数据。⑤ **本期 Windows 单机可能无 RAID 冗余，备份是唯一保护（R12）**，备份失败的后果比目标机更严重。

**必须配套**：备份日志（90 天、不含密钥）；每次备份后校验结果写入 `job_run.detail` 与审计；连续失败告警（ADR-005）；容量与介质状态纳入健康视图。

## 替换成本

| 场景                              | 成本（L3 估算）                                                                                     |
| --------------------------------- | --------------------------------------------------------------------------------------------------- |
| 换备份工具（如改 borg 或 rclone） | ≤1 天重写 `backup.sh` / `restore.sh` 与演练文档；对象存储目录格式不变，历史仓库需一次性转换（另计） |
| 调整策略（频率/保留/介质数量）    | ≤0.1 天（配置 + 检查单更新）                                                                        |
| 引入异地副本                      | 需新增介质与流程，超出 OQ-12 范围，需重新评审                                                       |

## 复评触发条件

1. 实测全库恢复超过 24 h（说明介质读速或数据量已超设计假设）。
2. 离线介质可用容量低于数据量的 1.2 倍。
3. 业务方将 RPO 收紧到 <24 h（需考虑 WAL 归档或更高频增量）。
