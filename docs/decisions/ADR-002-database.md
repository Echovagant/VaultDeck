# ADR-002 数据库与数据访问选型

| 项       | 内容                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 状态     | Accepted（2026-11-16）                                                                                       |
| 决策者   | 开发方（单人开发）                                                                                           |
| 关联     | `docs/design/design.md` §2.3、§2.6、§3.5、§4、§9.3；`ADR-005`                                                |
| 需求依据 | REQ-C-12（Repository 边界 + 迁移）、REQ-F-21/22（搜索与权限）、REQ-F-44/N-25（审计只追加）、REQ-N-06（并发） |

## 背景

需要同时承载：① 并发写（10 上传会话持续写会话/分片、20 下载写审计、统计与清理并发）；② 权限过滤（Leader 全量、Deputy 按项目、Member 按归属）；③ 文件名子串搜索；④ 只追加审计与按月归档；⑤ 统计聚合与每日快照；⑥ 任务互斥与补执行状态。

数据量按 3 年、20 万文件记录（L3 假设），远小于需要分库分表的规模；但**并发写与聚合**是真实需求，不能用单写者数据库勉强支撑。

## 决策

采用 **PostgreSQL 16 单实例**，数据访问用 **Kysely（类型安全 query builder）+ 手写 SQL 迁移脚本**。

- 迁移：`migrations/NNNN_xxx.up.sql` 与 `.down.sql`，单调递增、已发布不可修改；启动时发现 pending 即拒启动。
- 搜索：`lower(file_name)` 上建 `gin_trgm_ops` 索引，配合 `ILIKE`；<3 字符退化为顺序扫描，由应用层加前置过滤与 LIMIT（design.md §3.5）。
- 审计：`REVOKE UPDATE, DELETE`，按月分区，仅 INSERT/SELECT。
- 互斥：`pg_advisory_lock` 用于定时任务防重入（ADR-005）。
- **平台说明（ADR-007）**：Windows 下为官方 x64 二进制归档 + `pg_ctl register` 注册服务，程序目录与数据目录分离；`pg_trgm`、分区、`REVOKE`、`CONCURRENTLY` 均跨平台一致（Windows 无大页，性能略低，L3 待实测）。

## 备选方案与否决理由

| 方案                      | 否决理由                                                                      |
| ------------------------- | ----------------------------------------------------------------------------- |
| SQLite                    | 单写者模型；WAL 下写锁争用不可控；"未来换库不改业务"的目标反而更难达成        |
| MySQL / MariaDB           | 能力足够，但部分索引、`RETURNING`、JSONB、表达式索引均弱于 PG，无迁移收益     |
| Prisma                    | 需额外引擎二进制（离线可用但体积大、升级即换引擎），且 schema 与 SQL 双层维护 |
| TypeORM                   | 实体类型穿透到业务层，与 Repository 边界（REQ-C-12）冲突，隐式查询难以审计    |
| 引入 Elasticsearch 做搜索 | JVM 常驻 2–4 GB、离线包 500 MB+、需独立备份与权限视图同步；需求只是文件名子串 |
| Redis 做会话/缓存/队列    | 为一个 50 人系统增加常驻服务与运维面；会话查主键的延迟不是瓶颈                |

## 后果

**正面**：并发写与聚合能力充足；权限过滤、搜索、审计、快照在同一事务域内完成，无跨系统一致性；备份工具链成熟（`pg_dump -Fc` / `pg_restore` / `pg_verifybackup`）；迁移脚本可评审、可回滚。

**负面**：① 需自行运维 PostgreSQL（升级、参数、磁盘监控）；② 手写 SQL 与迁移的工作量高于 ORM 自动迁移，需配套 Code Review；③ trgm 对中文短词有性能上限（R8）；④ 单实例仍是单点，靠备份而非副本保证可恢复。

**参数约束**：`shared_buffers` 8 GB、应用连接池 20、`work_mem` 16 MB（design.md §9.3）；索引创建用 `CONCURRENTLY`。

## 替换成本

| 场景                              | 成本（L3 估算）                                                                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 换数据库（如改 MySQL 或 SQLite）  | 3–8 天：改 Repository 实现 + 迁移脚本 + 方言差异（`ILIKE`/trgm/`RETURNING`/分区），SQL 只在 `infrastructure/persistence/**`，业务零改动；不满足 1 工作日 |
| 换 query builder（Kysely → 其他） | 1–2 天，Repository 接口不变                                                                                                                              |
| 引入 Elasticsearch 作搜索后端     | ≤1 天接 `SearchPort` + 索引回填任务（回填耗时另计）                                                                                                      |

## 复评触发条件

1. `file` 表超过 500 万行且搜索 P95 持续 >2 s（R8 兑现）。
2. 并发上传超过 20 会话或审计写入成为写入瓶颈。
3. 需要多实例部署（此时需先解决会话共享与迁移锁，而非换库）。
