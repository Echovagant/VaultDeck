# ADR-005 定时任务与调度

| 项       | 内容                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 状态     | Accepted（2026-11-16）                                                                                                             |
| 决策者   | 开发方（单人开发）                                                                                                                 |
| 关联     | `docs/design/design.md` §2.8、§3.1、§3.8、§7.4、§8.5；`ADR-002`、`ADR-006`                                                         |
| 需求依据 | P1 §8.3 任务清单 T-01～T-06、REQ-F-49/50（清理与补偿）、REQ-N-19/20/21（严格 10 天、连续失败告警、启动校验）、REQ-N-29（健康视图） |

## 背景

需要 6 类周期性任务：回收站清理（T-01，每日 ≥1 次）、上传会话过期清理（T-02，每小时）、完整性巡检（T-03，每月）、统计快照（T-04，每日）、备份（T-05，每日/每周）、审计归档（T-06，每季度）。

它们的共同特征不是"高吞吐"，而是：低频、必须可追溯（谁在何时执行、结果如何）、必须能在失败或停机后**补执行**、必须有连续失败告警、必须与业务共享同一事务与审计域。单实例部署，无多节点调度需求。

## 决策

采用**应用内调度器 + 数据库任务台账 + 咨询锁 + 启动补偿 + CLI 兜底**：

1. 调度器按分钟 tick，读取 `setting` 中的 cron 表达式（可配置），到时触发。
2. 每次执行写 `job_run`（`job_name`、`scheduled_at`、`started_at`、`finished_at`、`status`、`attempt`、`error`、`detail`）。
3. 用 `pg_advisory_lock` 保证同一任务不会并发重入（即使未来误启多进程也安全）。
4. **启动补偿**：服务启动时扫描"应执行但未成功"的任务（按上次成功时间与周期推算），强制补执行；结果必须写审计（REQ-N-21）。
5. **连续失败判定**：查询 `job_run` 最近 2 次同任务状态，连续失败即写 `alert` 告警 Leader（REQ-N-20）。
6. **CLI 入口**：`vaultdeck job run <name>` 供运维手工触发与故障排查，与调度执行走同一套幂等逻辑。
7. 每个任务自身必须幂等：T-01 以 `trash_entry.status='pending' AND expire_at<=now()` 驱动；T-02 以 `upload_session` 过期状态驱动；T-04 用唯一键 `(project, date, category)` upsert。

**平台说明（ADR-007）**：Windows 下调度仍以应用内为主，但每 tick 用墙钟时间比对 `job_run.scheduled_at`（休眠会导致计时器漂移），系统 resume 后立即补扫；任务计划程序**只作备份兜底**，不承担主调度。**本 ADR 备选项中的"纯 systemd timer"在 Windows 平台的对应结论被 ADR-007 取代。**

## 备选方案与否决理由

| 方案                    | 否决理由                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| BullMQ + Redis          | 为每日级任务引入常驻队列中间件与一份离线包；单实例上无吞吐收益；增加故障面                       |
| 纯 systemd timer + 脚本 | 进程外调度天然隔离，但任务状态、连续失败、补执行、审计、健康视图仍需自建；与业务事务域割裂       |
| 外部 cron 直接调 HTTP   | 与 systemd 方案同类问题，且需暴露内部管理接口，增加攻击面                                        |
| pg-boss（PG 作为队列）  | 少一个组件，但引入队列表与轮询开销；需求规模不需要队列语义（不需要 worker 池、优先级、重试退避） |
| 云定时服务 / 平台调度   | 违反离线与局域网约束                                                                             |

## 后果

**正面**：无额外常驻服务；任务状态与业务同库，健康视图（`job_run` + `alert`）开箱可用；补执行逻辑统一，进程重启不漏任务；CLI 与调度共用逻辑，故障排查简单；advisory lock 防重入成本极低。

**负面**：① 调度依赖应用进程存活；应用未运行时业务本身不可用，因此可接受，但"备份"这类强独立任务需额外保障（M4 用发布检查单 + 手工 CLI 兜底）；② 长任务（巡检、备份）会占用进程资源，需限速与错峰执行；③ 单实例假设明确，未来多实例必须先改造调度（加分布式锁或外置调度）。

**执行窗口**：T-03 巡检按 11.41 TiB 顺序读估算约 6.6 h（L2，假设 500 MB/s），必须安排在非工作时段并限速，避免影响上传下载（REQ-N-15）。

## 替换成本

| 场景                                       | 成本（L3 估算）                                                         |
| ------------------------------------------ | ----------------------------------------------------------------------- |
| 换调度实现（如改 systemd timer 或 BullMQ） | ≤1 天重写 `SchedulerPort` 与 `JobRunner` 实现；任务处理器与幂等逻辑不动 |
| 换为多实例部署                             | 3–5 天（需外置调度或分布式锁 + 会话共享），超出本期范围                 |
| 调整任务周期                               | ≤0.1 天（改 `setting` 配置）                                            |

## 复评触发条件

1. 出现多实例部署需求（触发调度与锁的整体改造）。
2. 单任务执行时长超过其周期（如巡检跨日未完成）。
3. `job_run` 记录量与查询性能成为负担（可加分区与归档）。
