# ADR-001 后端框架选型

| 项       | 内容                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 状态     | Accepted（2026-11-16）                                                                                                          |
| 决策者   | 开发方（单人开发）                                                                                                              |
| 关联     | `docs/design/design.md` §2.2、§6、§9.1；`ADR-002`                                                                               |
| 需求依据 | REQ-C-02（前后端分离 + 单体后端）、REQ-C-10（外部能力经接口）、REQ-C-11（契约唯一）、REQ-C-14（1 天回退）、REQ-N-06（并发规模） |

## 背景

系统为单机、纯局域网、离线部署，规模为 50 账号 / 20 活跃 / 10 并发上传 / 20 并发下载 / 10 并发预览。核心负载是**大文件流式 IO**（8 MiB 分片、20 GB 单文件、流式打包），CPU 密集点集中在 SHA-256 校验、ZIP 写入与 Office 转换。

约束是单人在长期内维护前后端，且要求"换实现不改业务"（REQ-C-10/11）。这使"前后端类型与契约的共享成本"成为选型的首要权重，而不是极限吞吐。

## 决策

采用 **NestJS 11 + TypeScript，运行于 Node 24 LTS，单进程，Fastify 适配器**。

配套硬约束（与框架本身同等重要，写入工程规范）：

1. SHA-256、合并、ZIP 写入、Office 转换、批量导入解析**不得**运行在主事件循环：分别用 `worker_threads` 与子进程。
2. 禁止在请求链上使用同步 `fs` API（ESLint 规则强制）。
3. 不启用 `cluster`：单实例部署；若未来启用，分片与调度已用数据库锁与幂等键兜底。
4. `domain/` 与 `application/` 不得 import 任何 NestJS 符号，保证框架可替换（详见 design.md §6.2）。

## 备选方案与否决理由

| 方案                              | 否决理由                                                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Spring Boot（Java 21 + 虚拟线程） | 大文件与并发能力更强、生态更稳，但需维护 Java 与 TS 两套类型体系，契约类型无法直接共享，单人开发周期预计上浮 20%–30%（L3 估算） |
| Go + Gin / Echo                   | 部署最简（单二进制）、性能最好，但 OpenAPI 与类型生成生态较弱，前后端类型共享需额外生成层，单人前端协作成本更高                 |
| Python + FastAPI                  | 类型共享可行，但离线依赖管理与长期运行更脆弱；CPU 密集任务与 GIL 组合需要更多进程编排                                           |
| 纯 Express/Koa 自组装             | 少一层抽象，但 DI、模块边界、契约校验都要自建，与"低返工"目标相悖                                                               |
| 微服务 / Serverless               | 规模不成立；单机上进程隔离是伪隔离；Serverless 无法离线                                                                         |

## 后果

**正面**：前后端共享一套类型与契约；OpenAPI 生成链最短（ADR 见 design.md §5.1）；流式 IO 天然适配；单进程部署与离线打包简单；单人可在一套语言内完成全栈。

**负面**：① 单线程模型对"忘记移出 CPU 任务"极敏感，一处同步重计算即可拖垮全部请求；② Node 生态的长期稳定性弱于 JVM；③ 内存与 GC 行为需压测标定（design.md §9.1 的 2 GiB 上限是硬约束）；④ 大型企业级运维工具支持较少。

**监控指标**：事件循环延迟（`perf_hooks`）、RSS、worker 队列长度、`soffice` 子进程数。任一持续越界即视为架构风险复评信号。

## 替换成本

| 场景                                  | 成本（L3 估算）                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| 版本回退（同一框架降级）              | ≤1 工作日，满足 REQ-C-14                                                               |
| 替换框架（如改 Spring Boot 或 Go）    | 3–5 天重写 `interfaces/http` 与 DI 装配，**业务模块零改动**；不满足 1 工作日，如实标注 |
| 替换 HTTP 适配器（Fastify ↔ Express） | ≤0.5 天                                                                                |

## 复评触发条件

1. 实测事件循环延迟 P95 持续 >100 ms 且无法通过拆分 worker 解决。
2. 出现必须依赖 JVM 生态的组件（如仅 Java 可用的转换或检索），且无法用子进程隔离。
3. 单人维护成本在连续两个里程碑中超估 50% 以上。
