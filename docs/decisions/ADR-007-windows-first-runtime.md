## 背景

项目为个人长期开发，**只有一台 Windows 电脑**，不采购也不维护第二台机器。"部署到服务器"实际含义是"在自己这台机器上跑起来、让局域网其他人访问"，专用服务器操作系统的概率极小。

v0.3 设计假设 Linux LTS + systemd + XFS + POSIX 权限位 + apt 离线仓库，与真实条件不符，会让"安装、守护进程、证书、权限、定时任务"全部不可执行。技术栈本身（NestJS、Vue3、PostgreSQL、restic、LibreOffice）均为跨平台组件，因此**只需替换部署层与少数平台相关实现**，不动业务与契约。

## 决策

1. **运行环境**：Windows 10/11 x64 单机，Node 24 x64，应用单进程；开发、演示、验收同机完成。
2. **进程守护**：**WinSW**（单 exe + XML 配置）注册为 Windows 服务，支持崩溃重启、免登录会话运行、stdout/stderr 重定向到文件。
3. **PostgreSQL**：官方 x64 二进制归档（zip，非安装器）+ `pg_ctl register` 注册服务；程序目录与数据目录分离，数据目录位于 `${DATA_ROOT}\pgdata`；服务账户固定。
4. **反向代理**：**Nginx for Windows** 仅承担 TLS 终止、静态资源、API 反代、限流；**大文件下载改由 Node 流式下发并自行实现 Range**。原因是 Windows 构建为单 worker + `select` 模型、无 `sendfile`/`aio` 语义，`X-Accel-Redirect` 拿不到零拷贝收益；代价是多一次用户态拷贝，收益是**可即时 `destroy()` 下载流**（原 R7 缺口关闭）且不依赖平台专有机制。
5. **TLS 与 CA**：`openssl` 生成根 CA 与服务器证书；客户端在 Windows 证书管理器"受信任的根证书颁发机构"导入；**Firefox ESR 使用独立证书库，必须单独导入**。
6. **预览**：LibreOffice Windows MSI，`soffice.exe --headless` + 独立 `-env:UserInstallation`；超时用 `taskkill /PID <pid> /T /F` 回收进程树。
7. **备份**：restic Windows x64 单二进制 + `pg_dump`；备份介质**按卷标/GUID 解析**，不写死盘符；不使用 VSS（对象不可变 + 数据库逻辑备份已保证一致性）。
8. **定时任务**：仍以应用内调度为主（墙钟比对 + 启动补偿 + 系统 resume 后补扫）；任务计划程序**只注册 1 项备份兜底**，不承担主调度，避免双跑。
9. **路径**：物理路径**不含用户文件名**（内容寻址），天然规避 260 字符上限；统一 `path.join`，URL 与契约一律 `/`；同名唯一性由 DB `lower()` 索引保证，不依赖文件系统；`rename` 失败重试并映射为明确错误码。
10. **权限**：NTFS 只读属性 + 数据目录 ACL + 应用层不提供对象删除接口（如实说明：弱于 POSIX 权限位，但结合"应用无删除入口 + 引用计数 + 审计"可接受）。
11. **主机策略**：禁止睡眠/休眠、Windows Update 设活动时间并延迟重启、Defender 排除数据目录与对象区、防火墙仅放行 443（专用网络）与运维来源。

## 备选方案与否决理由

| 方案                      | 否决理由                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| Linux LTS 服务器          | 无第二台机器、不维护；REQ-C-19 明确本期仅 Windows 单机                                                 |
| Docker Desktop / WSL2     | 需要虚拟化层，离线镜像体积大，文件 IO 跨层更慢，单机无编排收益                                         |
| NSSM                      | 维护停更，日志与配置能力弱于 WinSW                                                                     |
| 任务计划程序常驻          | 无崩溃自动重启语义，需保存账户凭据，日志需自行重定向                                                   |
| Caddy on Windows 作主代理 | Windows 二进制质量更好，但无 `X-Accel` 等价，需鉴权端点 + 路径映射，暴露面与审计时序更复杂；保留为备选 |
| 本期做文件内容静态加密    | REQ-C-21 明确不做；BitLocker 作为后续可选方向                                                          |

## 后果

**正面**：零额外硬件；开发/验收同环境，减少"换环境才暴露"的问题；部署件就是 zip + 服务 XML，回滚只改指针文件；Linux 迁移路径完整保留（业务零改动）。

**负面**：① 本期**无 RAID 冗余**（可能单盘），备份是唯一保护（R12）；② 无 cgroup 内存硬限，改为应用内 RSS 软限 + 可选 Job Object（R5）；③ Defender 与 Windows Update 会干扰 IO 与可用性（R13）；④ 开发机兼服务端，资源与端口争用（R5）；⑤ Nginx Windows 单 worker，代理层并发能力有限（R10）。

## 替换成本

| 场景                    | 成本（L3 估算）                                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| Windows → Linux 目标机  | 3–5 天：部署脚本按平台分支 + systemd 单元 + 代理切回 `X-Accel` + 数据目录复制；业务与契约零改动 |
| WinSW → NSSM / 任务计划 | 0.5 天（仅服务封装层）                                                                          |
| Nginx → Caddy           | ≤1 天配置；Node 流式下发不变                                                                    |
| 引入 BitLocker（后续）  | 0.5 天运维操作（重启与密钥托管），不涉及代码                                                    |

## 复评触发条件

1. 目标塔式服务器到货并上机——这是"继续 Windows"还是"迁移 Linux"的正式决策点。
2. WinSW 在目标 Windows 版本上无法满足崩溃重启或免登录运行。
3. Nginx Windows 单 worker 在实测并发下成为瓶颈（切换 Caddy，或让 Node 直接终止 TLS）。
4. 需求方要求"磁盘离线即不可读"（启用 BitLocker 并重新评估性能与恢复流程）。
